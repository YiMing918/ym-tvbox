## 功能

- **产物就一个文件**：`peter_tvbox_pro.json`——一份给 TVBox / 影视仓类应用读取的配置（JSON 格式），装着站点、直播源、解析线路三类东西。你（或你的应用）真正要用的就是它；仓库里的其余文件，都是为「每天自动生产它」服务的。
- **sites（站点）**：约 220 条（硬顶 220，随上游每日浮动）——采集站（走资源站接口的）约 15 个 + 爬虫站（走解析规则抓取的）约 205 个，覆盖影视 / 4K / 动漫 / 短剧 / 体育 / 音乐 / 少儿 / 直播 / 网盘等类目（逐类名单见下方「收录内容」；精确数字以仓库内 `peter_tvbox_pro.json` 与每次运行日志的 `[done]` 行为准）。
- **lives（直播源）**：8 个直播频道列表源。
- **parses（解析线路）**：40 条解析 / 嗅探线路，播到需要解析的地址时由应用调用。
- **每日自动更新**：GitHub Actions 每天北京时间 05:30 跑一轮：抓 6 个上游源 → 两轮探活（慢响应接口单独复检）→ 智能去重合并 → 仅在内容有变化时才提交（细节见「更新机制」）。
- **合并保护（异常时保留上一版）**：可用上游少于 3 个、合并后站点少于 120 个、或比上一版骤降超过 20% 时，本轮直接放弃提交、保留上一份可用配置；单个上游临时不可用也会自动跳过，不拖垮整轮。采集接口与站点依赖文件（jar / 规则文件）都采用三态探活：只有连续两次确认失效才剔除，临时故障、403/限流等不确定结果一律保留，避免 Runner 网络与用户网络不一致时误删。

## 部署与使用

分两种：**只想用**——什么都不用部署，把上方原站的配置地址直接填进应用即可（跳到第 5 步）；**自己部署一份**——Fork 一份到你自己的账号，地址换成你自己的、自动更新在你自己仓库里独立跑，照下面 1–6 步走：

1. **Fork 本仓库**：打开仓库页 → 右上角 **Fork** → 建到你的 GitHub 账号下。
2. **启用 Actions（最关键的一步）**：进入你 Fork 的仓库 → **Actions** 页 → 点启用工作流。GitHub 默认关闭 Fork 仓库的 Actions，不启用就不会自动更新（原因见下方「Fork 部署与原站的区别」）。启用后可以先手动点一次 **Run workflow**（运行一次），不用等到凌晨。
3. **确认产物生成**：等工作流跑完（绿勾），看你仓库主页里 `peter_tvbox_pro.json` 的更新时间是不是刚刚——是，说明你这条生产线通了。
4. **拿你自己的配置地址**：把下面地址里的 `你的用户名` 换成你的 GitHub 用户名，二选一：
   - **推荐**：jsDelivr 镜像（CDN 镜像，国内拉取更快更稳）——`https://cdn.jsdelivr.net/gh/你的用户名/ym-tvbox@main/peter_tvbox_pro.json`（注意：镜像有缓存，刚跑完的一轮更新可能晚几小时才刷新过来；要立刻拿到最新版用下面 raw 地址）
   - **备选**：raw 源站直达（更新最及时）——`https://raw.githubusercontent.com/你的用户名/ym-tvbox/main/peter_tvbox_pro.json`
5. **填进应用**：打开影视仓（或 TVBox 类应用）→ 设置 → **配置地址** → 粘贴地址 → 确认，应用会拉取并加载站点列表。
6. **验收**：首页能看到站点分类、随便点开一个站点能加载影片列表，就是部署成功。此后每天北京时间 05:30 自动更新，你什么都不用管（应用每次启动重新读取配置时自动拿新版）。

## 更新机制

- **更新频率**：每天一次，北京时间 **05:30**（工作流定时 `30 21 * * *`，即 UTC 21:30）由 GitHub Actions 自动执行（也可在 Actions 页面手动触发）
- **更新流程**：抓取全部上游源 → 对采集接口进行两轮探活（慢响应接口单独复检）→ 智能去重合并 → 仅在内容有变化时自动提交
- **安全熔断**：当可用上游少于 3 个、合并站点少于 120 个、或比上一版骤降超过 20% 时，自动放弃本次提交，保留上一份可用配置；站点依赖的 jar / 引擎 / 规则文件被两次确认失效时，该站点会被剔除并在运行日志中注明，而不是留着一个打不开的条目
- **应用侧**：影视仓每次启动重新读取配置地址时，即可获取最新版本

## Fork 部署与原站的区别（为什么 Fork 后不会自动更新）

- **唯一原因：GitHub 默认关闭 Fork 仓库的 Actions**。这是平台规则，对所有仓库一视同仁，不是代码差异。本工作流**零密钥**（上游全是公开源，提交用仓库自带权限），所以 Fork 后去 **Actions 页点一次启用**，就能获得与原站同款的每日 05:30 自动探活更新，不用配任何 Secret。
- **产物地址不同**：用你自己仓库的 raw 地址（把配置地址里的用户名换成你的），或 jsdelivr 镜像地址（格式 `https://cdn.jsdelivr.net/gh/你的用户名/ym-tvbox@main/peter_tvbox_pro.json`）；内容因各自探活时刻的上游状态会有几个站点的细微差异，属正常。
- **60 天规则**：仓库长期无活动 GitHub 会停用定时任务；工作流带心跳保活，前提是已启用。被停了去 Actions 页重新启用即可。
- **两种更新别混**：内容更新（站点名单）由你自己的工作流每天跑，天然独立；逻辑更新（合并脚本改进）要手动 **Sync fork** 同步原仓库代码。

![Actions 工作流列表](https://gcore.jsdelivr.net/gh/YiMing918/ym-tvbox@main/docs/ym-tvbox-actions.png)
*仓库 Actions 页：左侧是工作流名单，右侧是历次运行记录；Fork 后先在这里把 update 工作流启用，之后每天 05:30 自动跑，绿勾即成功。*

## 故障检查与维修

- **先查 Actions**：仓库 Actions → update 工作流最近一次运行是否绿勾、几点跑的；红叉点进去看日志，多为某个上游临时不可达，次日自动重试，也可手动点 Run workflow（运行一次）。
- **再查产物**：仓库主页看 `peter_tvbox_pro.json` 的最后提交时间是不是今天凌晨；是今天 = 链路正常，问题在 App 侧（重读配置/重启 App）。
- **内容几天没变**：多半触发了安全熔断（可用上游 <3 或站点 <120 自动放弃更新、保留上一份好配置），是保护不是故障。
- 主 JSON 是自动生成的，**不要手改**（改了也会被覆盖）；要改逻辑改 `merge.py` 或工作流文件。其余见下方「常见问题」。

## 常见问题

**Q：配置地址填哪个？**
A：优先填 raw 直达地址；国内网络拉取缓慢时用加速地址，两份内容完全一致。

**Q：为什么今天打开站点变少了/没变？**
A：探活会剔除失效站点，数量小幅波动正常；若上游大面积失效触发安全熔断（可用上游少于 3 个或合并站点少于 120 个），本次更新会自动放弃、保留上一份可用配置，所以有时会「没变化」——这是故意的保护，不是坏了。

**Q：更新了但应用里还是旧的？**
A：在影视仓/TVBox 里重新读取一次配置地址（或重启应用）即可；应用侧有缓存，不会自动实时刷新。

**Q：网盘类站点要登录的是谁的账号？**

## 隐私

- 本仓库只有公开聚合的接口配置与合并脚本，**不含任何个人账号、密码或 Cookie**。
- 配置里「我的 XX 网盘」类条目是空白占位，使用者需在应用内登录**自己的**网盘账号才能用，与本仓库作者无关。
- 自动更新脚本只抓取公开上游配置并探活，不收集任何使用者数据。
- **关于第三方 jar（请知悉）**：爬虫站点依赖上游作者发布的 spider jar 文件（应用实际执行的代码），本配置只是转载引用、无法审计其内容。合并脚本已做的治理：带 md5 固定值的 jar 按「一个地址只认一个 md5」归一；站点自带的 **http 明文且无 md5** 的 jar 直接剔除（明文传输又无完整性校验，可被无声替换）；少量 https 无 md5 的 jar 靠 TLS 本身防篡改。继承自上游整仓 spider 的 jar 同样在剔除之列（2026-11-14 站长拍板严格执行：俊哥/小盒子/二月红等整仓接口因其 spider 为 http 无 md5 而下线，日志中逐条以 `[jar-drop]` 标明）。介意执行第三方代码的话，请只用采集站（type 0/1，不加载 jar）。

## 📦 使用方式 · 优缺点 · 已知问题（速览）

### 部署方法（两种）

- **推荐：直接用在线地址。** 把上文「配置地址」里的 raw 地址填到影视仓 / TVBox 类客户端的「接口地址」里保存即可，不需要服务器、不需要部署任何东西，配置每天自动更新，你这边什么都不用管。
- **自己维护一份：Fork 本仓库。** Fork 后开启仓库自带的自动更新流程，它会定时把上游内容合并生成到你自己的仓库里，再把客户端里的地址换成你仓库的 raw 地址即可。适合想完全自己掌控更新节奏的人。
- 说明：这个仓库是「配置文件」不是程序，所以没有服务器部署一说；换地址只换配置，你客户端里的收藏、历史记录都不受影响。

### 优点

- 不是单一来源：聚合多个公开上游，自动合并、去重，一份配置当好几份用。
- 每天自动更新，不用手动到处找新接口地址。
- 收录前会做可用性筛选，失效、重复的内容会被清掉，列表相对干净。
- 点播、解析、直播一份全包，填一个地址就够。

### 缺点 / 要花钱的地方

- 完全免费，0 元；不需要域名、不需要服务器。
- 内容不是自营的：上游源失效、改版、关停都会直接影响可用性，这是所有聚合配置的共同问题。
- 部分境外源在国内网络直连打不开，需要你自己的代理环境才能看。

### 和同类有什么不同

- 很多流传的配置是某个人一次性导出的快照，过期就废；这份是自动流程每天重新聚合生成的活配置。
- 出于安全考虑，没有完整性校验的第三方脚本包（jar）不会被收录——宁可少几个源，也不让来路不明的代码进客户端。

### 已知问题 / 注意事项

- 某个站点时好时坏多半是上游在变动，等下一次自动更新通常会修正或剔除。
- GitHub 的定时任务偶尔会延迟几小时，配置日期差一点属正常现象。
- 直播源稳定性普遍弱于点播源，个别频道打不开请优先换线路/换源。
