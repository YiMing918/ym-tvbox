# 红果源全自动维护流水线（hongguo-watch）说明

这条流水线是给红果源配的「自动巡检员」：它住在 GitHub 的服务器上，每天
自己醒来两次，替你把红果源检查一遍、上游有更新就留档、状态有变化就记账，
全程不用你动手，也不用任何人盯着。它和你仓库里原来那条每天 05:30 合并
TVBox 配置的流水线（update.yml）是两条独立的线，互不干扰。

## 一、它每天自动干什么

每天北京时间 **06:10** 和 **18:10** 各跑一次（也可以在仓库的 Actions 页
手动点一次）。每次跑，它依次做四件事：

1. **盯上游**：把 drpys 的《红果漫剧.py》拉下来，先验明正身（文件大小
   正常、代码能编译、关键功能都在），再和上次记录的指纹（SHA-256 哈希）
   对比。上游改了、且验明是好的，就把新版存一份到 `hongguo/upstream/`
   里留档；上游要是传上来一个坏文件，坏文件不进留档，只记一笔。
2. **真探活**：用兜底核心（`hongguo_core.py`，就是映匣/影视仓在用的那份
   的可读版）真的去调一遍红果的接口——注册一个匿名设备、搜一次
   《总裁是我前女友》、打开它的详情数集数、拉一次第一集的弹幕。
   不是 ping 一下装样子，是把用户要走的路真的走一遍（播放除外，见下）。
3. **看社区还活着没**：顺带记一笔两个上游仓库（drpys、hongguo-drama）
   最近一次提交是什么时候。这两个仓库只要还在更新，就说明写源的人还在，
   红果哪天改版，他们大概率会跟上修。
4. **记账，有变化才提交**：结果写进 `hongguo/status.json`。只有真有变化
   （某一环坏了或好了、上游文件更新了、上游仓库有新提交了）它才会往仓库
   里提交一次，提交信息里写清变了什么；没变化就安安静静结束，不产生
   一堆空提交。提交后顺手清一下 jsDelivr 缓存，让 status.json 对外
   立刻是最新版。

## 二、什么情况你会「无感恢复」

- **上游作者修好了源**：比如 drpys 的搜索哪天又坏了，作者改完一提交，
   你的壳本来就会自己拉新版；这条流水线额外保证：新版在进你手机之前，
   已经被验过一遍是好的、还留了档。万一新版反而更坏，留档里还有上一版。
- **接口小抖动**：红果官网接口偶尔会抽风返回空结果。巡检的搜索环节自带
   一次重试，不会因为一分钟的抖动就把状态记成「已坏」，你更不会收到
   假警报。
- **签名小轮换**：如果红果只是小改接口、社区作者跟上了，整条链是：
   作者更新 → 流水线发现并留档 → 你的壳自动拉到 → 恢复。你什么都不用做。

## 三、什么情况它也无能为力（先说清，不糊弄）

- **红果换全新签名、且全社区都没修出来的时候**：播放签名是逆向出来的，
   每次大轮换都要有人重新破解。在社区修好之前，谁家的红果源都播不了，
   这条流水线也变不出来——它能做的是第一时间把「详情/搜索还行、社区
   还在更新」这些状态如实记下来，让你知道是全网的问题、不是你手机的
   问题，更不是源被谁删了。
- **播放这一环，它永远验不了**：红果的播放接口对机房 IP（GitHub 的
   服务器出口也算）一律返回空白，这是字节的风控。所以 status.json 里
   播放永远写的是 `unverifiable`（无法验证），这是事实陈述，不是故障。
   播放到底通不通，只有你的手机能验。这也是为什么 overall 状态里
   不把播放算进去——不拿一个永远验不了的环节吓唬人。

## 四、status.json 怎么看

在仓库 `hongguo/status.json`，用浏览器或 GitHub 打开就能看：

- `checked_at`：这份状态生成的时间（北京时间）。注意它只在「有变化」
  时才更新提交，所以时间旧不等于流水线死了——去 Actions 页看
  hongguo-watch 的运行记录，那个才是每次巡检的打卡。
- `overall`：总评。`healthy` = 四环全通；`degraded` = 有一环打折
  （比如弹幕拉到 0 条）；`broken` = 搜索或详情断了，源基本不可用。
- `steps`：四环明细。`register` 设备注册、`search` 搜索、`detail` 详情、
  `danmaku` 弹幕，每环有 `status`（ok/fail/degraded/skipped）和一句
  人话 `detail`（比如「《总裁是我前女友》共 95 集」）。
- `playback`：播放环，`status` 基本恒为 `unverifiable`，原因写在
  `note` 里；`attempt` 是每次尝试取址的原始结果，只作参考。
- `upstream`：上游文件的指纹 `sha256`、大小 `size`、校验结果
  `validation`、这次有没有留档 `archive_synced`、上游这个文件最近
  一次提交时间 `file_last_commit_at`。
- `community`：两个上游仓库最近提交时间。`hongguo-drama` 基本天天
  更新；`drpys` 是周更到月更的节奏，长时间没动静才值得留意。

## 五、和仓库里其他东西的隔离

- 独立文件 `.github/workflows/hongguo-watch.yml`，不改动、不依赖
  update.yml / test.yml / release-pack.yml 任何一个。
- 时间错开：它 06:10、18:10 跑，合并流水线 05:30 跑，不抢同一时刻。
- 它提交时只碰 `hongguo/status.json` 和 `hongguo/upstream/` 两个路径，
  仓库里其他文件它一律不碰；万一和别的提交撞车，它会像 update.yml
  一样自动 rebase 重试 3 次。
- 权限最小：只要 `contents: write`（提交巡检结果用），没有其他权限。

## 六、上传启用清单（只做一次）

把下面这些放进仓库 `YiMing918/ym-tvbox` 的对应位置，流水线就活了：

| 本地文件 | 仓库里的位置 | 说明 |
|---|---|---|
| `hongguo-watch.yml` | `.github/workflows/hongguo-watch.yml` | **必须放这个路径**，放错地方 GitHub 不认 |
| `tools/hongguo_watch.py` | `hongguo/tools/hongguo_watch.py` | 巡检脚本本体 |
| `hongguo_core.py` | `hongguo/hongguo_core.py` | 巡检要 import 它，仓库里必须有这份 |
| `status.json` | `hongguo/status.json` | 初始样本，之后由流水线自己更新 |
| `upstream/红果漫剧.py` | `hongguo/upstream/红果漫剧.py` | 上游留档初始版，可传可不传（流水线会自己同步） |

启用后去 Actions 页确认 `Hongguo source watch` 出现，手动跑一次
（Run workflow）看它变绿，就齐活了。之后它自己运行；GitHub 有个
「60 天无活动停用定时任务」的规矩，但你这个仓库每天有合并提交，
不会触发，不用操心。

## 七、本地自测结果（2026-11-27，沙箱实跑）

脚本在沙箱里真跑了多遍，结论如下：

- **全链探活通过**（样本 status.json，2026-11-27 16:14 北京时间）：
  设备注册 ok（服务端下发真实 device_id/iid）；搜索 ok（「总裁是我
  前女友」10 条）；详情 ok（95 集）；弹幕 ok（第 1 集 2 页拉到 67 条）；
  播放 unverifiable（尝试取址得到空响应，与预期一致，只记事实）。
  overall = `healthy`，单次全程约 12–17 秒。
- **上游留档通过**：拉到 drpys《红果漫剧.py》206,126 字节，编译与关键
  定义校验通过，SHA-256 = `10fd79ad43e912f5…`，已同步到
  `upstream/红果漫剧.py`，留档文件本地复验可编译。
- **社区信号通过**：drpys 仓库最近提交 2026-11-13、其红果文件最近
  提交 2026-09-14；hongguo-drama 最近提交 2026-11-27（当天），
  社区活跃度与 UPSTREAMS.md 的普查一致。
- **「无变化不提交」通过**：状态稳定后连跑，脚本判定 `变化=False`，
  status.json 前后 MD5 完全一致，工作区零 diff。
- **两个实测中发现并已修的坑**：① 官网搜索偶发一次空返回——已给搜索
  环加了「隔 3 秒重试一次，两次都空才记 fail」；② GitHub API 在沙箱
  共享 IP 下会被限流（403），取不到提交时间时已改为沿用上次记录值，
  不再误报「有新提交」。Actions 环境里脚本会带 GITHUB_TOKEN 调用
  API，限额高得多，这两个坑在正式环境只会更轻。
- **workflow 语法校验通过**：hongguo-watch.yml 经 YAML 解析无误，
  cron 为 `10 22 * * *` 与 `10 10 * * *`（UTC），即北京时间
  06:10 与 18:10；权限仅 `contents: write`；actions 版本与
  update.yml 使用同一组钉版 SHA（checkout v4 / setup-python v5）。
